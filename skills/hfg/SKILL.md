# /hfg：規劃交接給較弱模型

**使用者打 `/hfg <需求>` 的意思是：這個 session 用的是較強的模型，請把「想清楚」這件事在這裡做完。**

產物是一份**施工規劃書**。它的讀者是另一個 session 的較弱模型，那個模型**看不到這段對話**、不會主動查 CLAUDE.md、也不會回頭問你。規劃書就是它的全部上下文。

---

## 硬規則

| | |
|---|---|
| **不寫入任何專案檔案** | 不用 Edit／Write 改專案程式碼，即使你已經完全知道怎麼改。要改的內容寫進規劃書的步驟裡，讓執行者去貼。**唯一可以 Write 的是規劃書本身。** |
| **必須做偵察，不准憑記憶** | Read／Grep／Glob／跑測試／開瀏覽器看現況都要做。**沒有真的打開檔案就不准寫行號**——錯的行號比沒有行號更糟，執行者會直接信。詳見下方「偵察的四個最低標準」。 |
| **有疑問先問，不准硬猜** | 見下方「提問閘門」。**規劃書裡不准留 TBD／「視情況而定」／「請確認」／「兩種都可以」。** |
| **技術取捨當場決定** | 有客觀較優解的分岔點在這裡決定並寫死，附一行理由。不要把選擇權留給執行者。 |

## 偵察的四個最低標準（2026-08-15 實戰補上，每一條都真的害執行者卡住或走錯方向過）

**1. 每一個 `old_string` 都要驗證唯一性，不准憑印象宣稱「這個字串唯一」。**

```bash
grep -c "要當 old_string 的那行" <檔案>
```

回 2 以上就代表你得加上下文，或者——**更重要的**——代表這個專案裡有結構相同的姊妹函式／重複區塊，
那通常意味著**要改的地方不只一處**。實例：某專案裡兩個並排的圖表元件共用同一組座標轉換函式，
一字不差，原規劃只打算改一個，真那樣做兩個圖表的軸線會對不齊，而測試與語法檢查都抓不到。
**字串不唯一是一個訊號，不只是一個技術障礙。**

**2. 對真實資料檔下任何筆數斷言之前，必須全檔清點。**

`head`／`sed -n '1,40p'` 看到的是抽樣，不是事實。要寫進驗收判準的數字一律用 `grep -c`／`wc -l`
對全檔數一遍。實例：用 `head -40` 看一份匯入清單就斷言「有兩筆符合某分類」，真實是 8 筆，
執行者做對了卻被錯的判準卡住。**判準寫錯比沒有判準更糟——它會讓正確的實作被判定成失敗。**

**3. 改 UI／視覺／互動之前，先想辦法真的看到現況。**

讀 CSS 與模板字串推斷出來的「病灶」很容易是錯的。實例：使用者回報「某個數值擠到分隔線上」，
純讀程式碼推斷成外層容器的 padding 問題，**方向完全錯**——真正的病灶是圖表元件裡
最後一筆資料點壓到旁邊的標籤文字，而那要看到畫面才會知道。多繞了一整輪提問才問出來。

- 開得起來 → 開瀏覽器／跑起來看。**優先用 DOM 幾何量測而不是截圖目視**——
  「這兩個元素有沒有重疊」用 `getBoundingClientRect()`／SVG 座標算得出精確數字，
  目視只能說「看起來還好」。而且量測結果可以直接寫進驗收判準，目視不行。
- `file://` 常被擋。先看專案有沒有 `.claude/launch.json` 的 static server 設定；
  port 被佔用時多半是使用者自己開著的同一個 server，**直接連過去就好**，不用另開。
- 開不起來（權限、要登入、要真實資料）→ **在規劃書明寫「本次診斷基於程式碼推斷，未經視覺確認」**，
  並把「確認病灶是否正確」列進第 1 節「執行者驗不了」那段。不要讓推斷偽裝成觀察。

⚠ **幾何相關的修正要掃參數的極端值，不能抽測一個。**
實例：兩個圖表元件的重疊修正，在資料量大的視窗量測是「餘裕 2.2px、通過」，
切到資料量小的視窗才發現某個元素寬度沒有上限、撐到 80px、壓過標籤 24px——
**同一份程式碼、不同視窗，結論相反。** 只測一種參數等於沒測。
純函式能擷取到 node 直接跑更好：不依賴頁面載入狀態，而且一次掃六種視窗只要幾秒。

**4. 驗證步驟要排在「最後一個會動到該檢查項的工作項之後」。**

不要把驗證放在它第一次相關的工作項裡就不管了。先掃一遍所有工作項，
問「哪一項是最後一個會影響這個驗收的」，把驗證排在它後面。
實例：同步驗證放在工作項 B 和 G，但工作項 D 排在更後面又改了同一份來源檔，
收尾時同步檢查是 FAIL——規劃書的排程漏洞，不是執行者的錯。

## 提問閘門（寫規劃書之前必過）

**這是唯一還能問到使用者的時機。**規劃書一旦交給執行者，它不會回頭問——你沒問的問題就變成它亂猜的地方。

出現以下任一情況，**必須先用 AskUserQuestion 問，拿到答案才動筆寫規劃書**：

- 需求裡有你自己也不確定答案的疑問
- 需求可以有兩種以上合理解讀，而不同解讀會做出不同的東西
- 涉及使用者的意圖或偏好（要什麼行為、什麼算「做對了」、UI 長怎樣、口徑怎麼定）
- 取捨沒有客觀較優解（例如效能 vs 可讀性、改動範圍大小、要不要保留舊行為）
- **會改變第 1 節驗收標準的任何事**
- 偵察後發現現況與需求的假設不符（檔案結構不是預期的、要動的東西已經被改過）
- 需求可能牽涉超出使用者預期的範圍（要動到既有邏輯、架構、資料口徑）

反過來，**不要問**這些——這些是你該自己決定的：有客觀較優解的實作細節、可以從程式碼／CLAUDE.md／既有慣例讀出答案的事、問了也不影響產出的事。查得到就去查，不要拿問題換懶惰。

提問的形式要求：

- **每個選項都附後果**：選了會做出什麼、動到哪些檔案、驗收標準會變成什麼。不要只給選項名稱。
- **給推薦**：把你建議的放第一個並標「(建議)」，理由寫在 description 裡。使用者請你規劃，不是請你出考卷。
- **一次問完**：AskUserQuestion 一次最多四題，把所有卡點合併成一輪，不要一題一輪來回。
- 答案拿到後，寫進第 5 節「已做掉的決策」，理由欄註明「使用者選定」——執行者才知道這條不准自行改。

分不清該問還是該自己決定時：**問**。多問一輪的成本是三十秒，猜錯的成本是整份規劃書和執行者的工都白做。

## ⚠ 視覺設計類任務：先做 mockup，不要急著出規劃書

**先判斷：這次是「修正畫面的錯誤」還是「改變畫面的長相」？**

| 任務性質 | 例子 | 做法 |
|---|---|---|
| **修正錯誤** | K 棒壓到標籤、標籤跑出畫面、比例算錯、元素越界 | 照常出規劃書，直接改 |
| **改變長相** | 「這區塊不好看」「要更專業」「重新設計」「整體感覺很亂」 | **先做 mockup，使用者確認方向之後才出規劃書** |

實測代價（2026-08-16 一天內）：卡片 UI 改了**九個版本**，其中**兩次做了又移除**、
四次方向錯誤。每次都有實測數據支持、每次都解決了當下被指出的問題，
但使用者看完的結論仍是「整體設計搭配概念很差」。

原因：**逐次微調解決不了「整體感」的問題。** 每個元件單獨看都合理，
放在一起卻是五種視覺語言——因為從來沒有先定義過設計系統（字級階梯、間距、
圓角、色彩語意），每次改動只能憑當下感覺，而不同時間的感覺不會一致。

**做法**：

1. 先產出 mockup（HTML widget 或圖，**不碰專案程式碼**）
2. 附上「我認為目前的 N 個視覺問題 ＋ 修改策略」——讓使用者確認的是**判斷**，不只是圖
3. 使用者確認方向後，才進入下面的產出流程
4. **mockup 階段自己做，不要派 subagent**——它需要來回迭代與使用者確認，派工反而慢

⚠ 同時要盤點「參考範例沒有、但這個專案不能丟掉的東西」。照搬別人的漂亮設計時，
最容易把專案特有的功能一起丟掉——那些通常正是它與同類產品的差異點。

## 產出流程

1. **偵察** — 讀目標檔案、確認函式名與行號、確認測試目前是綠的（是紅的就要寫進前置條件）、讀當前專案的 `CLAUDE.md`（以及它指向的 skill／文件）挑出**跟本次任務相關**的陷阱。
2. **列出所有分岔點** — 逐個判定：我自己決定，還是要問使用者？（依上方閘門）
3. **提問閘門** — 有任何一項要問，就先問完。**沒拿到答案不准往下寫。**
4. **寫規劃書** — 用下面的模板，九個區塊照順序，一個都不能省。
4b. **交付前自我稽核** — 見下方「交付前的機械稽核」。**這一步不准跳過，也不准靠印象代替。**
5. **交付** — 預設寫成檔案（要貼給另一個 session 才是主要用途），路徑 `plans/HFG_<任務slug>_<YYYY-MM-DD>.md`（`plans/` 不存在就建）。同時在對話裡摘要三行：做什麼、動到哪些檔案、驗收怎麼跑。使用者說「直接顯示」才只顯示不落檔。
6. **派工** — 規劃書寫完後，看有沒有可用的施工執行者 agent（`.claude/agents/` 底下，或使用者全域的 `~/.claude/agents/`，常見名稱 `builder`）：
   - **有** → 直接用 Agent tool 派工，prompt 只要給規劃書路徑與「照它執行」。agent 卡住時**自己**查證並修規劃書，再用 SendMessage 讓它繼續，**不要把卡點丟回給使用者**。
   - **沒有** → 輸出下方那段開場句，讓使用者自己轉貼到另一個 session。
   - 使用者說「只要規劃」「先給我看」時 → 停在第 5 步，不要自己派工。
7. **驗收** — **自己跑第 1 節的每一項，不採信 agent 的完工報告。** 實際發生過：agent 回報「全部完成」，但某個步驟的副作用沒被規劃書的驗收涵蓋，同步檢查其實是失敗的。

**派工時的兩個選擇：**

- **model**：預設 `sonnet`（`builder` 已寫死）。逐字級步驟它足夠，而且行為契約守得住。
  **不要用 haiku**——「該停就停」的紀律它守不住，會自己補完。需要現場判斷的步驟多到得用 opus 時，
  代表**規劃沒做完**，回去把那些步驟寫死，不是升級模型。
- **要不要拆成多份規劃書**：判準是**工作項之間有沒有依賴**。互相獨立的可以拆開分批派、
  各自驗收；有依賴的必須留在同一份，並在第 6 節開頭明寫執行順序（例如「照 C→F→E→A→B→D 做」）。
  單純因為「檔案很長」而拆是錯的理由——拆散有依賴的步驟，執行者就看不到全貌了。

## 施工中的意外處理（派工者的責任，不要丟回給使用者）

**情境一：執行者停下回報，而規劃書真的寫錯了**

1. **自己查證**現況，不要採信執行者的判斷，也不要採信自己的記憶——跑指令。
2. **修規劃書本身**，不要只在對話裡口頭更正。執行者的唯一指令來源是那份文件。
3. 修訂處要**留痕**：在該節開頭加一行 `⚠ <日期> 修訂：原本寫 X 是錯的，實際是 Y`。
   後人（和你自己下一輪）才知道判準為什麼長這樣。
4. 已經做完的步驟標成 `✅ 已完成，不要重做`，並在續傳訊息裡明寫**從哪一步繼續**。
5. 用 SendMessage 續傳時，**明確要求它重讀被改動的那一節**——不要假設它會自己發現文件變了。
   ⚠ 實測踩過：規劃書改了，執行者仍照它第一次讀到的版本回報，導致雙方對「做到哪」認知不一致。

**情境二：發現範圍外的既有缺陷擋住驗收**

1. **先判定是既有的還是本次造成的**——查證，不要猜。（實例：某個匯出腳本的純度檢查失敗，
   查它依賴的名單發現漏了一個項目，是四天前就壞的，與本次改動無關。）
2. **既有缺陷要不要順手修，是使用者的決定，不是技術決定**——這是範圍擴大，用 AskUserQuestion 問，
   附上「不修的代價」與「修的成本」。
3. 決定要修 → 加成新的工作項，**同時補進第 1 節驗收表與第 3 節檔案清單**，不要當成臨時插隊。
4. 決定不修 → 調整原驗收判準繞過它，並在規劃書寫明「這關為什麼放行」。

## 交付前的機械稽核（第 4b 步）

> **為什麼要有這一節**：實測三次施工中斷，全部落在「驗收判準」與「定位資訊」上，
> **沒有一次落在「該做什麼」**。設計決策是健康的，弱的是事實查證。
> 而那三次都不是能力問題，是**當下沒想到要查**——所以解法不能是「下次記得」，
> 必須是一份交付前照著跑的清單。

**A. 事實稽核——規劃書裡每個具體事實，都必須是某條指令的輸出**

規劃書裡出現的行號、筆數、「目前值是 X」、「這個字串唯一」、「共 N 個」，
逐一問自己：**我是用哪條指令查到的？** 答不出來就是沒查，現在補查。

最低限度要重跑這三種：

```bash
grep -c "<每一個 old_string 的首行>" <檔案>   # 必須回 1，回 2 以上要處理
grep -c "<要寫進判準的關鍵字>" <真實資料檔>    # 筆數斷言一律全檔數，不准用 head 抽樣
grep -n "<要引用的目前值，如版本碼>" <檔案>    # 確認寫進規劃書的是現值不是記憶
```

⚠ **最危險的不是「不知道」，是「為沒查證的宣稱編一個理由」。**
實例：規劃書寫「這個字串唯一（另一個函式用的是不同寫法）」——括號裡那句是憑空補的，
而真相是兩個函式一字不差。**沒查就寫「未確認」，不要用推論填空。**

**B. 覆蓋稽核——規劃書內部的一致性**

- 每一個驗證步驟：往下看，**還有沒有工作項會影響它？** 有的話驗證要往後移。
  （實例：同步驗證放在工作項 B 和 G，但工作項 D 排更後面又改了同一份來源檔，收尾時檢查是 FAIL）
- 每一個步驟的「依賴」欄：標的是不是真的依賴？漏標會讓執行者用錯順序。
- 第 1 節每一項驗收：是不是真的**有某個步驟會讓它從失敗變成通過**？
  沒有對應步驟的驗收項，不是驗收，是願望。
- 第 3 節檔案清單：第 6 節有沒有步驟要改清單外的檔案？有就是清單漏了。

**C. 不可逆稽核——哪些步驟做了收不回來**

第 6 節逐步掃一遍，把**不可逆**的步驟挑出來，在該步標 `⚠ 不可逆`：
刪檔／覆蓋既有檔案／`rm -rf`／資料庫 migration／部署／對外發送／改動線上設定／
撤換金鑰／改動使用者資料。

不可逆步驟要多兩樣東西：

- **前一步做備份或快照**（非 git 專案尤其必要，見下方「先確認這個專案的條件」）
- **該步的「不符怎麼辦」不准寫「停下回報」就結束**，要明寫「已經做到哪裡、怎麼還原」

可逆的步驟（改程式碼、加註解、跑唯讀指令）就照常，不要每步都當成高風險——
**全部標成危險等於沒有標。**

**D. 誠實稽核**

通篇搜一次這些詞：「應該」「可能」「大概」「照理說」。
出現在**事實描述**裡就是沒查證的訊號——去查，或改寫成「未確認，執行者遇到不符就停下回報」。

---

**做完這四項稽核仍然會有錯**，那是規劃的本質：它是對現況的預測，而現況會變。
但**可機械檢查的錯誤要降到零**——剩下的交給執行者的行為契約接住，那才是它存在的理由。
執行者停下回報不是失敗，是安全網生效；真正的失敗是它沒停、自己補完、而你沒發現。

## 規劃書模板

````markdown
# 施工規劃書：<一句話任務名>
> 這份文件是你這次任務的**唯一指令來源**。不要另外推測需求，不要做這裡沒寫的事。
> 遇到與本文件描述不符的現況 → 直接跳到最後一節「卡住時怎麼辦」。

## 0. 前置條件（開工前逐項確認，任一不成立就停下回報）
- [ ] <檔案路徑> 存在，且 <某函式> 在第 <N> 行附近
- [ ] `<測試指令>` 目前是全過的（若本來就紅，停下回報，不要當成自己弄壞的）
- [ ] <其他會讓本規劃書失效的假設>

## 1. 目標與驗收標準
**完成後長這樣**：<一句話>

**怎麼確認做對了**（每項都要能執行、都要有預期輸出）：
| 檢查 | 指令／操作 | 預期輸出 |
|---|---|---|
| 功能 | `<指令>` | `<具體字樣／數字>` |
| 回歸 | `<原有測試指令>` | 全過，項數不少於開工前 |
| 回歸 | 清單外檔案未被修改 | 只有第 3 節列出的檔案有變動 |

**⚠ 執行者驗不了的部分**（視覺、互動、需要真實帳號或外部服務的）：
> 這一段直接寫給使用者看，執行者不要嘗試模擬。
- <具體要看什麼、在哪裡看、看到什麼算對>

---

**寫這一節的兩條規則：**

- **分清楚「機器可判定」與「只能人眼看」。** 前者寫成指令＋預期字樣；後者**明確標成使用者的工作**，
  並在第 2 節禁止執行者「自己想辦法模擬」。沒有分清楚的話，視覺層會被當成已完成——
  執行者回報「全部完成」，但根本沒人看過畫面。
- **專案沒有自動測試時，不准把驗收寫成「確認功能正常」。** 改用這些具體形式：
  指令的實際輸出字樣／檔案內容的 `grep -c` 計數／產物檔案的存在與大小／
  跑一段拋錯即失敗的 `node -e` 檢查。**寧可驗收項少但每項都能機器判定，也不要一堆空話。**

## 2. 範圍邊界：明確不要做的事
- 不要重構 <X>，即使看起來很亂
- 不要加防禦性程式碼／try-catch／參數檢查，除非某步驟明寫要加
- 不要動 <檔案／目錄>
- 不要改變數名、不要調整格式、不要順手修無關的 typo
- 不要新增檔案，除非某步驟明寫
- 不要改測試來讓測試過
- 不要 commit、不要開分支、不要 push、不要動 stash <！-- git repo 才寫這條，見下方說明 -->
- 不要嘗試模擬第 1 節標成「執行者驗不了」的那些檢查

## 3. 相關檔案清單
| 檔案 | 讀/改 | 相關位置 | 為什麼相關 |
|---|---|---|---|
| `<path>` | 改 | `<函式名>`（約 L<n>–L<m>） | <一句話> |
| `<path>` | 只讀 | `<函式名>`（約 L<n>） | 參考既有寫法，不要改 |

**不在這張表上的檔案都不要開、不要改。**需要全專案搜索才找得到的東西，代表這份規劃書漏了——回報，不要自己找。

## 4. 本次相關的已知陷阱
> 只列跟這次改動相關的。每條寫清楚「會怎麼踩到」和「具體避法」。
- **<陷阱名>**：<為什麼會踩到>。→ **做法**：<具體怎麼避>。

## 5. 已做掉的決策（不要重新評估）
| 分岔點 | 決定 | 理由 |
|---|---|---|
| <A 還是 B> | <A> | <一行> |

現場狀況與某條決策矛盾時 → 停下回報，不要自行改採另一案。

## 6. 逐步操作
> 逐字級：`old` 要與檔案完全一致（含縮排），`new` 是要貼進去的完整內容。
> **新建檔案的步驟**用 Write 並附上完整檔案內容，不要只寫「建一個做 X 的檔案」——
> 那等於把設計丟回給執行者，違反「技術取捨當場決定」。內容長就長，這是規劃該付的成本。

### 步驟 1：<做什麼>
- **工具**：Edit `<path>`
- **old_string**：
  ```
  <原文>
  ```
- **new_string**：
  ```
  <新內容>
  ```
- **預期結果**：<Edit 成功／某輸出出現>
- **依賴**：無／必須先完成步驟 N，因為 <原因>

### 步驟 2：<驗證步驟>
- **指令**：`<指令>`
- **預期結果**：`<具體輸出>`
- **不符怎麼辦**：停下回報，不要繼續下一步

## 7. 完成後自我檢查清單
- [ ] 第 1 節每一項驗收都真的跑過，輸出符合預期（貼出實際輸出）
- [ ] 第 2 節「不要做的事」一件都沒做
- [ ] 只改了第 3 節列出的檔案
- [ ] 第 4 節每個陷阱的避法都照做了
- [ ] <任務特有項，例如：BUILD 日期碼已更新為 MMDDx>
- [ ] 回報裡附上第 1 節「執行者驗不了」那段，原文轉給使用者
- [ ] 有任何一步偏離規劃書 → 在回報裡明寫哪一步、為什麼

## 7b. 完工後要更新的文件（由派工者做，不是執行者）
> 這一節寫給派工者自己看。驗收過了不等於結案——沒寫進文件的決策，下一輪就會被重新討論一次。
- <該專案記錄改動的地方，例如 CHANGELOG／開發日誌／現況節>
- <本次產生的新規則或新陷阱，要寫進 CLAUDE.md 或對應 skill>
- 規劃書本身補一節施工紀錄：**實際卡在哪、規劃書哪裡寫錯、判準改成什麼**

## 8. 卡住時怎麼辦（行為契約）
出現以下任一情況，**立刻停下**，輸出「卡在第 N 步 ／ 預期 X ／ 實際 Y ／ 已完成到第 M 步」，然後等指示：
- 某步的預期結果沒出現
- `old_string` 找不到或不唯一
- 需要改清單外的檔案
- 驗收指令失敗
- 覺得規劃書某處是錯的

**明確禁止**：嘗試規劃書沒寫的替代方案、擴大搜索或改動範圍、為了讓驗收通過而改測試或改判準、跳過失敗的步驟往下做。**回報一個做到一半但誠實的狀態，遠勝於一個自己補完的版本。**
````

## 寫作要求

- 具體優於抽象：「跑 `node tests/run_tests.js`，最後一行要是 `全部通過`」而不是「確認測試通過」。
- 每個「不要做」都要是**這次任務真的可能被順手做掉的事**，不是通用道德勸說。
- 步驟預設逐字級。真的需要現場判斷才降級成描述級，並在該步註明「此步需判斷，判準是 X；不確定就停下回報」。
- 陷阱只列相關的。全抄 CLAUDE.md 會稀釋注意力，反而讓真正致命的那條被忽略。
- 沒有派工 agent 時，規劃書寫完檔後在對話裡附一段可直接複製給執行者的開場句：
  > 請完整讀 `plans/HFG_xxx.md` 並依其執行。那份文件是唯一指令來源，不要做文件沒寫的事；任一步預期結果沒出現就停下來回報，不要自己找替代方案。

## 先確認這個專案的條件（每次都要，不同專案差很多）

寫規劃書之前先確定三件事，它們會改變模板要怎麼填：

| 確認什麼 | 怎麼查 | 影響 |
|---|---|---|
| **是不是 git repo** | `git rev-parse --git-dir` | 是 → 第 2 節必須寫「不要 commit／開分支／push／動 stash」；範圍驗證用 `git status --porcelain`，改壞了可以還原。不是 → 刪掉那條禁令，但**第 0 節要加一步「先備份要改的檔案」**，見下方 |
| **有沒有自動測試** | 看 `package.json` scripts、`tests/`、CI 設定 | 有 → 第 0 節寫「開工前測試是綠的」、第 1 節放回歸項。沒有 → 見第 1 節那兩條規則，用可機器判定的替代形式，**不要退化成「確認功能正常」** |
| **執行者驗得了多少** | 這次改動是不是要看畫面／要真實帳號／要外部服務 | 驗不了的部分寫進第 1 節「執行者驗不了」那段，並在第 2 節禁止它模擬 |

執行者的工具權限也要順帶想一下：預設的執行者 agent 通常只有讀寫檔案與跑指令。
如果驗收非得開瀏覽器不可，那要嘛派工時放寬權限，要嘛就老實把那部分歸給使用者。

**⚠ 不是 git repo 的專案：沒有安全網，要自己造一個。**

沒有 git 就沒有 `diff`、沒有 `checkout` 還原——執行者改壞了主檔（尤其是那種上萬行的單檔專案），
就是真的壞了。所以第 0 節前置條件要加一步，且第 1 節驗收表的「清單外檔案未被修改」
必須給得出可執行的指令，不能只是一句期望：

```bash
# 開工前（第 0 節）：備份這次會動到的檔案
cp <目標檔> <目標檔>.bak_<YYYYMMDD>

# 驗收時（第 1 節）：確認只有預期的檔案被改、且改動幅度合理
diff <目標檔>.bak_<YYYYMMDD> <目標檔> | head -50
```

備份檔用完由**使用者**決定要不要刪，執行者不准刪、也不准拿它當還原手段自己回退——
發現改壞了要停下回報，還原是使用者的決定。
